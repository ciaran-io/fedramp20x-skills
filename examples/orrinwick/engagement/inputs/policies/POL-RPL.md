## Purpose

Orrinwick can restore the offering and its data within its stated objectives.

## Scope

All Orrinwick staff and contractors, and every information resource marked in scope in mas/mas-record.json.

This policy covers these information resources from the scope record:

| ID | Resource |
|---|---|
| P3 | Managed relational database |
| P4 | Object storage |
| P12 | Cross-region backup replica storage (us-west-2) |
| E3 | Infrastructure as code state and runners |
| P1 | Production cloud accounts and network |

## Requirements

| ID | Requirement | KSIs |
|---|---|---|
| RPL-1 | The recovery objectives are a recovery time of 8 hours and a recovery point of 4 hours. The Platform Lead reviews them at least every 90 days and records the result in environment/recovery-objectives.json. | KSI-RPL-RRO |
| RPL-2 | Backups run at least every 2 hours, are encrypted and are copied to a second US region (P12) into a vault that has a compliance-mode lock. Backup jobs and copy jobs are monitored every day. A failed job raises an alert within 60 minutes, and a named person acknowledges it. | KSI-RPL-ABO |
| RPL-3 | The recovery plan describes how a recovery environment is built from infrastructure code and how data is restored into it. It is kept in step with the architecture. | KSI-RPL-ARP |
| RPL-4 | A restore test runs at least every 6 months. It records the time taken, the data age restored and any failure. | KSI-RPL-TRC |
| RPL-5 | The recovery environment, once built, falls under the same scope record and controls as production. | KSI-RPL-ARP |

## Exceptions

An exception needs a written request, a named risk owner, a compensating control and an expiry date of no more than 90 days. The GRC Lead records approved exceptions in docs/security-decision-record.md. An expired exception is a policy violation.

## Enforcement

Violations are reported to the GRC Lead. Staff violations follow the personnel security process (N5).
